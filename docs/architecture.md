# 系统结构

```text
JSON 工具定义 / 调用示例
          │
          ▼
共享检索核心 ── 本地 SQLite 目录、原始 JSON、向量、generation
    │          ▲
    │          └── QGIS 与独立程序可以打开相同数据库文件
    ▼
EmbeddingProvider
    ├── HTTP → 本机或远端 /v1/embeddings
    └── 隔离 worker → llama.cpp → CPU / GPU

GUI / CLI / HTTP service → 后台任务 → 共享检索核心
QGIS native runtime     → 后台任务 → 同一共享检索核心
```

共享 SDK 只依赖 Qt Core/Network 与 SQLite。QGIS 编译这部分代码，不链接独立程序的 Qt DLL、llama.cpp 或 GPU 后端。独立产品在 SDK 之上提供 UI、服务和推理 worker。

## 记录与语义文档

每条记录保存原始 payload，并使用独立字段表示来源、记录类型、能力标识和可用性。`definition` 表示工具定义，`example` 表示一次调用形式。多个示例可以关联到一个能力，排序结果按能力聚合，原始示例仍可按记录 ID 读取。

语义文档提取名称、用途、参数和值以及输入输出线索。临时请求 ID、确认标记等不参与匹配，绝对路径被规范化，避免每次换目录都改变工具用途。原始 JSON 不会因此被修改。

JSON 中的任何命令、路径或 `confirmed_risk: true` 都只是数据。本产品不因检索命中而执行它们。QGIS 执行器需要重新解析实时能力、绑定实际数据并遵守原工具的确认规则。

## 检索与持久化

核心使用归一化向量的余弦相似度召回，再结合精确标识符与关键词召回，以 RRF 进行排序。中文和英文需求使用相同接口。RRF 是排序分数，不能解释为“正确概率”。

完整 schema 按需读取。首屏候选的摘要用于缩小模型需要阅读的定义数量，不把全部工具 JSON 同时发送给聊天模型。

向量缓存归属于 embedding profile。profile 包含模型版本、维度、归一化和提示模板版本，不包含服务地址。因此两台设备提供同一向量空间时可以复用同一本地数据库。

目录同步按 source 提交完整快照，向量计算在后台进行。写入者使用跨进程协调和短 SQLite 事务。查询读取已发布 generation，迟到结果必须核对当前记录及 profile，不能覆盖较新定义。

Embedding 服务不可用时，查询可降级到关键词检索，但结果明确显示 `retrieval_mode: lexical`。质量验收不把这种降级当作语义检索通过。

## QGIS 接入

QGIS 导出工具、具体 Processing 算法、Binary 程序和 Skills 的定义。共享核心负责候选召回，原 MCP 服务继续负责参数校验与执行。网关与后端规划器不属于独立匹配器的运行依赖。

QGIS 的向量请求使用 HTTP provider，连接本机与连接远端时不会切换到另一套目录数据库。独立程序可用于建立、检查、更新和查询同一数据库。

接口、数据库内容和服务设置分别有版本。共享核心通过有版本的源码包及哈希清单交给 QGIS，由 QGIS 自身工具链编译。修改应先进入独立仓库，再同步快照，避免产生两套无法一致更新的检索实现。
